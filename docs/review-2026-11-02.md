# Code check, 2 November 2026: things done oddly

Each says where it is, why it is odd, what could go wrong, and a suggested
fix. Most important first.

**Done on 3 November 2026:** 1 (one `localToday()`; History shows local
times), 2 (the CLI sets the rate when it opens books), 3 (`taxable` in place
of `rate: 15`), 5 (Reconcile keeps fields it does not decide), 6, 7, 8, 9,
and the dead code in 13. **6 was smaller than it reads below:** saves to a
folder or online already say when they fail; what was wrong is that a rule
that failed to save was still marked as saved. The rest (4, 10, 11, 12 and
`innerHTML` in 13) are in `backlog.md`.

## 1. "Today" is often the date in London, not New Zealand

`new Date().toISOString().slice(0, 10)` gives the UTC date. In New Zealand
that is still *yesterday* until 1pm in summer (noon in winter). It is used in
84 places. A few pages already do it properly with
`toLocaleDateString("en-CA")` (books.ts, contacts-page.ts, au-payroll-page.ts),
so the app has both kinds of "today".

What shows it:
- A new invoice or bill made in the morning is dated yesterday
  (`invoices.ts:196`, `bills.ts:46`).
- Recurring invoices due today are not made until the afternoon
  (`recurring.ts:25`).
- The aged receivables/payables "as at" date is yesterday (`aged-report.ts:47`).
- Payroll pay-period defaults and "has finished" checks (`payroll.ts:541, 851, 1050`).
- The `at` date on every coding and filed return.

Fix: one `todayLocal()` in one place, used everywhere. A lint check could
then forbid `toISOString().slice(0, 10)` for "today".

## 2. The GST rate is one setting shared by everything

`packages/core/src/sales-tax.ts` keeps the rate in a module variable
(`current`), NZ's 3/23 unless something calls `setSalesTaxFraction`. The web
app sets it when books open (`country.ts:37`). The **CLI never sets it**, so
`osabooks gst` on Australian books works out GST at 3/23, not 1/11. Anything
that ever holds two sets of books at once (the MCP server, the nightly job, a
test) has to remember to set it, and it changes for everyone at once.

Fix: pass the rate in with the books (or the jurisdiction) rather than as a
global. As a stopgap, set it in the CLI where it loads the ledger.

## 3. "15" means "taxable" on invoices and bills, even in Australia

`invoices.ts:150-175`: the tax types are Xero NZ's names ("15% GST on
Income") with `rate: 15`, and `rateOf()` returns 15 for Australian names and
for "10%". The number is only used as "is there GST", and the real tax comes
from the global rate in 2, so the figures come out right. But it reads as
15% in Australian books and invites a mistake.

Fix: a `taxable: boolean` (or the treatment) in place of a rate. Offer each
country its own names ("GST on Income" / "GST on Expenses" in Australia).

## 4. A text note used as a status flag

The one fixed tonight (Keep mine looked at the note to know a line was
settled) was not the only place where words double as data:
- `coding-reconciliation.ts:963` still accepts the old note as the marker, for
  lines kept before the fix. Fine, but it can't be dropped until old books
  have been saved again.
- Reconcile writes "Suggestion accepted unchanged" and "Changed by hand, no
  description given" as notes (`reconcile-page.ts:2438`). They read like
  descriptions, and in exports and History they sit where the person's own
  words go.

Fix: keep a separate `how` field ("accepted", "changed", "kept", "imported")
and leave `note` for words a person typed.

## 5. Confirming a line on Reconcile rebuilds its override from scratch

`reconcile-page.ts:2427` writes a whole new override, so any other field on
it is lost: `claimIn` (claim the GST in a later return), `keptAgainstImport`,
and anything else added later. `claimIn` can only be set from the CLI today,
so confirming that line again in the app silently moves its GST claim back.

Fix: start from the existing override and replace only the fields the page
decides, as Keep mine does. And if `claimIn` is meant to be used, give it a
place in the app; if not, take it out.

## 6. Save failures that nobody hears about

Some saves happen in the background, and their failures are thrown away:
- `persistRules().catch(() => undefined)` (`reconcile-page.ts:2633`): a rule
  made by coding a line can fail to save and the page says nothing. It shows
  up later as rules that "forgot" themselves.
- `record(...).catch(() => undefined)` (`reconcile-page.ts:2466, 2632`): the
  History entry can be lost without a word, and History is what Undo relies on.

The ledger save on the same tick does report a failure (`state.persistent = false`).
The rules and History saves should too.

## 7. Accept all can accept rows you can't see

On Coding reconciliation's rule proposals (`coding-reconciliation.ts:3875`)
the table shows the first 200, with no "showing 200 of N" note, while
"Accept all N" takes every one. The other long tables say "Showing the first
200 of N". This one should too, or Accept all should only take what is shown.

## 8. Imports that assume New Zealand dollars

Lines are given "NZD" when the file doesn't say, even in Australian books:
- Expense claims built from journals: `currency: "NZD"` always
  (`packages/core/src/expense-claims.ts:135`). The Xero AU demo's claims come
  in as NZD.
- Xero invoice CSV with no Currency column (`packages/core/src/invoices.ts:287`).
- Akahu (`akahu.ts:242`) is NZ only, so that one is right.
- The bank importers do take `context.defaultCurrency`, so they are fine when
  it is passed.

Fix: the books' currency passed down everywhere, never a literal "NZD".

## 9. Typed money read the NZ way only

`parseMoney` in `invoices.ts:278` strips commas and multiplies by 100:
- "12,50" (how many countries write $12.50) becomes $1,250.00.
- Anything it can't read becomes 0, silently, on an invoice line.
- It ignores currencies with no cents (JPY, KRW), which `moneyPlaces()` knows
  about.

The core already has `parseAmount(input, currency)`, which the assets and
Australian payroll pages use. Invoices and bills should use it too, and
refuse rather than zero what they can't read.

## 10. Thirty-three copies of "format money"

There are 33 local `money()` / `dollars()` / `formatMoney()` functions in
the web app. Some wrap `booksMoney`, some rebuild it with `toLocaleString`,
and some (`grants-page.ts:84`) use `toFixed(2)`, which ignores the books'
currency places. They already differ on negatives (brackets in some, a minus
sign in others).

Fix: two shared ones, one for the screen and one for reports with brackets,
and remove the rest.

## 11. History order trusts each computer's clock

Event ids start with the time on the computer that made them, and "is there
a later change" (`events.ts`, `canReverse`) compares ids as text. With you
and the accountant on two computers, a clock a few minutes out puts changes
in the wrong order, so Undo can be offered when it shouldn't be, or refused
when it should be allowed.

Fix: online, let the server stamp the time; or keep a running number per
set of books.

## 12. Very large files

`reports.ts` (5,952 lines), `coding-reconciliation.ts` (4,524),
`excel-export.ts` (3,125), `reconcile-page.ts` (2,946), `store.ts` (2,416).
Each holds several unrelated pages or features, which is how problems like 7
go unnoticed: the same idea (a long table, "Accept all") is built three ways.
`docs/refactor-plan.md` already covers some of this. Splitting
`reports.ts` per report would be the biggest win.
